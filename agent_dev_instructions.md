# Agent Development Instructions

This document outlines the core principles and interaction patterns for developing in the Winnie Da Pooh repository.

## Core Interaction Principles

- **MUST READ: Science Mindset**: In this repo, success will often rely on a scientific mindset -- know your assumptions, hypothesis, goal, and tests then iterate till you reach your goal while learning about the problem space via experimentation and exploration.
- **Notes over .md files**: Do not create new documentation files for specific modules or experiments. Instead, write notes; "lessons learned," or dos/donts at the bottom of the relevant Python script in the same syntax as currently implemented.  
- **Maintain `DOCUMENTATION.txt`**: This is the single source of truth for the repository's architecture and usage. If you add a new feature, task, or forecasting method, you MUST update `DOCUMENTATION.txt`.
- **Schema is Sacred**: Always ensure data remains consistent with the canonical schema defined in `src/common/schema.py`. Use Pydantic models for validation during ingestion and processing.
- **Testing Hygiene**: When testing logic or investigating data, prefer creating a temporary `.py` file (e.g., `temp_investigate.py`) rather than running long command chains or complex code directly in the terminal.
- **Use `uv`**: This project uses `uv` for dependency management and execution.
    - Install: `uv sync`
    - Run scripts: `uv run scripts/some_script.py`
    - Run experiments: `uv run runner/runner.py`
- **Data-First Approach**: Always touch and explore the data (using `scripts/inspect_parquet.py`) and explore the existing code before starting any implementation. Understand the shape of the `MarketRecord` and `TimeSeriesPoint` you are working with.
- **Hugging Face SQL Console**: The dataset is often available on Hugging Face (see `carpetxie/winniethepooh`). You can use the DuckDB-powered SQL console there for rapid data exploration.
    - **Usage**: Since the data is generated by `scripts/build_db.py`, the schema is discoverable in the code, but the console is useful to understand data distributions, verify edge cases, or check data quality on a larger scale than local samples. Start with `SUMMARIZE train;` to see current column stats.
    - **Workflow**: Find a natural stopping point in your investigation, provide the SQL code to the human, and ask them to run it on HF and return the results. This is preferable when local data is limited and you want to verify findings on the full remote database. 
- **Data Availability & Isolation**: 
    - The core .parquet containing market data may need to be re-loaded from (`\runner\runner.py`). 
    - **Multi-Agent Isolation**: To avoid confusion when multiple agents are building different datasets, use the `--name` flag in `scripts/build_db.py`. This isolates both the intermediate SQLite database (`data/clean/canonical_{name}.db`) and the final output folder (`data/datasets/v..._{name}_unified`).
    - **Workflow for custom data**:
        1. Build isolated dataset: `uv run scripts/build_db.py --name my_experiment --start 2024-01-01 --end 2024-01-31`
        2. Run isolated experiment: `uv run runner/runner.py --dataset data/datasets/v..._my_experiment_unified --name my_run`
    - Cleanup temporary datasets and `.db` files when finished to keep `data/` clean.

## Project Workflow

1.  **Exploration**: 
    - Read `DOCUMENTATION.txt` to understand the component you are working on.
    - Use `scripts/inspect_parquet.py` to see the current state of the database.
2.  **Implementation**:
    - Follow existing patterns for `ForecastMethod` (in `methods/`) and `Task` (in `dataobject/tasks/`).
    - Register new components in the appropriate registry (e.g., `methods/registry.py`).
3.  **Verification**:
    - Create a temporary script to verify your changes if they are complex.
    - Run the test suite: `uv run python tests/run_tests.py` or `uv run pytest`.
4.  **Documentation**:
    - Update the "LESSONS LEARNED" or notes at the bottom of the files you modified.
    - Update `DOCUMENTATION.txt` if necessary.

## Technical Nuances

- **Pydantic V2**: All fields in `BaseModel` must have type annotations.
- **Enums**: Inherit from `(str, Enum)` for seamless JSON and Parquet serialization.
- **Parquet Storage**: Data is stored in `data/clean/unified_market_data.parquet`. The pipeline is designed for speed (e.g., bulk S3 downloads for Kalshi).
- **Experiment Artifacts**: All run results, models, and plots are stored in `data/outputs/` and are ignored by git.
